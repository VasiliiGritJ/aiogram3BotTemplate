# DEV_WORKFLOW.md

## Цель

Сделать разработку максимально автономной, но безопасной для начинающего владельца проекта.

## Роли

- ChatGPT: продуктовый архитектор и ревьюер. Определяет scope этапа, принимает продуктовые решения, проверяет результат и обновляет `NEXT_TASK.md`.
- Codex в VS Code: локальный исполнитель. Читает инструкции из репозитория, меняет код, запускает локальные тесты, исправляет обычные ошибки и готовит локальный commit, если это разрешено текущей задачей.
- Владелец: подтверждает только внешние/рискованные действия, вручную проверяет ключевой UX в Telegram и принимает продуктовые решения, которые нельзя безопасно вывести из спецификации.

## Ежедневный рабочий цикл

1. ChatGPT обновляет `NEXT_TASK.md` в рабочей ветке.
2. Codex получает короткую команду: синхронизировать ветку, прочитать инструкции и выполнить `NEXT_TASK.md` автономно.
3. Codex сам:
   - анализирует релевантный код;
   - реализует scope;
   - запускает тесты;
   - исправляет ошибки своей реализации;
   - проверяет diff;
   - при разрешении создаёт локальный commit.
4. Codex останавливается перед push и просит одно подтверждение.
5. После push ChatGPT проверяет commit/PR через GitHub и обновляет следующую задачу.

## Что не должно требовать участия владельца

Если интерфейс/права среды позволяют, не нужно отдельно согласовывать:

- чтение файлов репозитория;
- поиск по коду;
- редактирование файлов в scope задачи;
- создание временных файлов и временных БД для тестов;
- `git status`, `git diff`, `git log` и другие read-only проверки;
- запуск `unittest`, compile/import checks и локальных тестовых скриптов без внешнего эффекта;
- исправление обычных ошибок, вызванных текущими изменениями;
- повторный запуск тестов после исправления.

## Что требует остановки/подтверждения

- push;
- изменение `main`;
- force push, rebase с переписыванием опубликованной истории;
- удаление/очистка реальной `db.db` или пользовательских данных;
- чтение/вывод реальных секретов;
- реальные запросы, требующие секретов, если задача этого явно не предусматривает;
- реальные платежи и массовые сообщения;
- системные настройки Windows, Git, VPN;
- деплой/production-инфраструктура;
- установка новой зависимости, если её не утвердили заранее;
- существенное расширение scope.

## Правило защищённой локальной БД

Пока `db.db` остаётся отслеживаемым исторически и содержит локальную тестовую запись владельца:

- считать его защищённым локальным файлом;
- не включать его в staging;
- не делать `git checkout -- db.db`, `git restore db.db` или удаление без отдельного решения;
- миграции тестировать на новой временной БД и копии;
- позднее отдельным этапом безопасно перестать отслеживать runtime DB после проверки создания БД с нуля.

## Контроль качества перед commit

Минимум:

1. релевантные тесты зелёные;
2. `git diff` просмотрен;
3. staged-список содержит только ожидаемые файлы;
4. `storage/.env` и runtime `db.db` не staged;
5. нет случайных секретов или отладочного вывода;
6. scope задачи выполнен без скрытого расширения.

## Контроль качества после push

- локальный HEAD совпадает с удалённой рабочей веткой;
- `main` не изменён;
- `git status` содержит только заранее известные локальные изменения;
- ChatGPT может независимо увидеть новый commit через GitHub.

## Шаблон команды Codex

После появления новой задачи обычно достаточно:

`Синхронизируй рабочую ветку. Прочитай AGENTS.md, PROJECT_SPEC.md, ROADMAP.md, DEV_WORKFLOW.md и NEXT_TASK.md. Выполни NEXT_TASK.md автономно по правилам конвейера. Остановись только на стоп-факторе или перед push. Все объяснения пиши по-русски.`
