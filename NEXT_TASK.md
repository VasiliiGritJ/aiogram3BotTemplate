# NEXT_TASK.md

## Текущая задача: Stage 2 — библиотека упражнений и детерминированный недельный план

### Цель

На основе уже сохранённого фитнес-профиля назначать пользователю конкретный недельный тренировочный план из контролируемой библиотеки упражнений и шаблонов. Выбор должен выполняться обычным детерминированным кодом без AI, быть воспроизводимым, сохраняться в БД и отображаться пользователю.

Каждый назначенный план должен содержать требования из `PROJECT_SPEC.md`:

- тренировочные дни;
- упражнения;
- порядок упражнений;
- количество подходов;
- целевой диапазон повторений;
- отдых между подходами;
- короткую понятную подсказку к упражнению.

## Принятый baseline Stage 1

Stage 1 полностью принят в живом Telegram:

- onboarding успешно пройден;
- профиль сохранён;
- trial создаётся ровно один раз и рассчитан ровно на 3 дня;
- централизованный access-service возвращает `status=trial`;
- миграции 1 и 2 применены;
- FSM-fix commit `8a0e87f` вошёл в merge commit `350cf9792e8ff280db55b8678ccf3eb8e7da4575`;
- merge commit запушен в `develop/fitness-coach-foundation`;
- реальная `db.db` остаётся локально modified и является защищённым файлом.

Не повторять приёмку Stage 1 и не откатывать её данные.

## Scope и порядок выполнения

Работать небольшими последовательными фазами. Перед каждой фазой проверять, что изменения остаются в scope Stage 2.

### Фаза 1. Исследование текущего кода и данных

1. Проверить текущую ветку и `git status`.
2. Изучить существующие модели, механизм миграций, сервисы профиля/доступа, onboarding и текущие способы показа пользовательских данных.
3. Зафиксировать фактические сохраняемые значения полей onboarding, которые влияют на план: цель, опыт, число тренировок в неделю, оборудование/зал, длительность и ограничения.
4. Спроектировать минимальную схему библиотеки, шаблонов и назначенного пользователю плана без изменения уже принятых сущностей Stage 1 сверх необходимого.

### Фаза 2. Воспроизводимая миграция 3 и модели

1. Добавить миграцию 3 через существующий механизм миграций проекта.
2. Добавить минимальные SQLAlchemy-модели для упражнений, структуры недельного плана и назначенного пользователю плана.
3. Обеспечить внешние ключи, ограничения целостности и предсказуемый порядок дней/упражнений.
4. Миграция должна безопасно обновлять схему и сохранять существующие данные.
5. Проверять создание схемы с нуля и обновление после миграций 1–2 только на временной БД или отдельной копии. Реальную `db.db` не использовать для схемных и бизнес-тестов.

### Фаза 3. Контролируемая библиотека и шаблоны

1. Добавить небольшую контролируемую библиотеку упражнений с необходимыми для выбора полями: название, категория или мышечная группа, оборудование, короткая подсказка и поддерживаемые ограничения/теги.
2. Добавить несколько явных недельных шаблонов под уже поддерживаемые цели, частоту тренировок и доступное оборудование.
3. В каждом шаблоне явно задать дни, порядок упражнений, подходы, диапазон повторений и отдых.
4. Данные библиотеки и шаблонов должны воспроизводимо создаваться обычным кодом или миграцией, без свободной генерации и без AI.

### Фаза 4. Детерминированный выбор плана

1. Реализовать отдельный сервис выбора шаблона по фактическим текущим значениям onboarding.
2. Учитывать поддерживаемые значения цели, опыта, числа тренировок в неделю, оборудования/зала, длительности и ограничений в той мере, в которой это однозначно следует из сохранённого профиля и контролируемых правил.
3. Одинаковый профиль и одинаковая версия библиотеки должны давать одинаковый результат.
4. Для неизвестного, устаревшего или частично заполненного значения использовать явно заданный безопасный fallback, а не случайный выбор или падение.
5. При заявленных ограничениях действовать консервативно: не ставить диагноз и не добавлять упражнение, явно несовместимое с поддерживаемым тегом ограничения. Если безопасное правило нельзя вывести из требований, остановиться перед продуктово значимым решением.

### Фаза 5. Сохранение и просмотр назначенного плана

1. Сохранять назначенный пользователю недельный план в БД, включая его дни и упражнения в фиксированном порядке.
2. Не создавать дубликат активного плана при повторном запросе без явной причины пересоздания.
3. Добавить понятный русскоязычный просмотр плана через существующую архитектуру бота, не запуская реальный Telegram API в рамках этой задачи.
4. При просмотре показывать для каждого дня упражнения по порядку, подходы, диапазон повторений, отдых и короткую подсказку.

### Фаза 6. Тесты и итоговая проверка

Добавить и запустить тесты как минимум для:

- создания новой схемы с миграциями 1–3 на временной БД;
- обновления временной БД после миграций 1–2 до миграции 3 без потери существующих данных;
- ограничений и связей новых моделей;
- воспроизводимого создания контролируемой библиотеки и шаблонов;
- детерминированного выбора для поддерживаемых значений профиля;
- безопасного fallback для неизвестных или неполных значений;
- учёта поддерживаемых ограничений;
- сохранения полного недельного плана и стабильного порядка его элементов;
- отсутствия дубликата активного плана при повторном запросе;
- отображения всех обязательных полей плана;
- отсутствия регрессии тестов Stage 1.

Все схемные и бизнес-тесты выполнять только на временной БД или отдельной копии. Не читать и не изменять реальную `db.db`.

- Использовать текущий стек: Python 3.12, aiogram 3, SQLite, SQLAlchemy и существующий механизм FSM/миграций.
- Использовать только уже существующие зависимости проекта; новую зависимость не добавлять.
- Не переписывать архитектуру проекта и не расширять Stage 2 до проведения тренировок, истории или прогрессии.
