# NEXT_TASK.md

## Текущая задача: Stage 1.2 — onboarding и trial/access-service

### Цель

После завершения этой задачи новый пользователь должен пройти короткий фитнес-onboarding, подтвердить анкету, получить 3-дневный trial и видеть заполненный профиль и текущий доступ. Без AI, без YooKassa и без тренировочного плана.

## Scope

Реализовать только:

1. FSM onboarding.
2. Поля анкеты:
   - возраст;
   - пол;
   - рост;
   - вес;
   - цель: `muscle_gain` / `fat_loss`;
   - опыт: `beginner` / `some_experience`;
   - тренировок в неделю;
   - длительность тренировки;
   - ограничения/травмы, допускается «нет».
3. Валидацию числовых ответов с понятными сообщениями.
4. Экран подтверждения анкеты перед записью.
5. Сохранение `FitnessProfile` и создание `UserAccess` в одной транзакции.
6. Trial начинается только в момент подтверждения анкеты и длится ровно 3 дня.
7. Централизованный сервис доступа без поля `status` в БД:
   - `active`, если действующая подписка;
   - иначе `trial`, пока `now < trial_ends_at`;
   - иначе `expired`;
   - ровно в `trial_ends_at` trial уже истёк.
8. `/start`:
   - завершённый профиль → обычное меню;
   - профиля нет → onboarding.
9. Профиль показывает фитнес-данные и текущий статус доступа/дату окончания.
10. Unit tests для валидаторов, сохранения профиля/trial и временных границ access-service.

## Продуктовые решения

- Интерфейс — русский.
- `weight_kg` уже хранится как Float.
- Незавершённый onboarding может храниться только в MemoryStorage и после перезапуска начинаться заново — это допустимо для MVP.
- Trial не начинается на первом `/start`; он начинается только после подтверждения анкеты.
- Не создавать поле `status` в `user_access`.
- Все даты доступа создавать/сравнивать в UTC по стратегии проекта.
- Цель и опыт выбирать кнопками.
- Ограничения — свободный короткий текст; ответ «нет» сохранять как `None` или эквивалентно нормализовать в сервисе.

## Ограничения

Не делать в этой задаче:

- AI/LLM;
- YooKassa/платежи;
- тренировочные программы;
- напоминания;
- админское управление подпиской;
- новые внешние зависимости;
- деплой;
- миграции реального `db.db`;
- удаление/откат локального `db.db`;
- чтение или вывод `storage/.env`;
- реальные Telegram API вызовы для автотестов.

## Работа с БД

- Существующие миграции Stage 1.1 считать фундаментом.
- Автотесты использовать на временных БД.
- Реальную `db.db` не менять в автоматических тестах.
- Если для ручной Telegram-проверки позже понадобится применить миграции к реальной БД, остановиться и запросить отдельное подтверждение владельца до изменения файла.

## Проверки

Минимум:

1. Все существующие тесты Stage 1.1 продолжают проходить.
2. Валидные/невалидные возраст, рост, вес, частота и длительность покрыты тестами.
3. Профиль и trial создаются согласованно.
4. Trial = ровно 3 дня от подтверждения.
5. `trial` до границы, `expired` ровно на границе и после неё.
6. Действующая subscription имеет приоритет над trial.
7. Истёкшая subscription не даёт `active`.
8. Нет реальных сетевых вызовов Telegram/YooKassa.
