- `PRAGMA quick_check = ok`;

- уникальность `users.tg_id` и SQLite foreign keys проверены;
- резервная копия настоящей БД сохранена вне репозитория;
- `db.db` локально изменён и не должен попадать в Git;
- `storage/.env` существует локально и игнорируется Git.

1. Проверить, что текущая ветка — `develop/fitness-coach-foundation`.
2. Не выполнять дополнительный fetch/merge, если локальный HEAD уже содержит Stage 1.2 и нет явного указания на новую удалённую задачу. Не создавать лишние запросы разрешений ради повторной синхронизации.
3. Проверить, что `db.db` не staged и `storage/.env` игнорируется Git, не выводя содержимое `.env`.

5. Убедиться по безопасным логам, что polling стартовал без traceback. Не выводить Bot Token и другие секреты.
6. Остановиться и попросить владельца вручную в Telegram:

   - появилась ровно одна запись `user_access`;
   - `trial_started_at` и `trial_ends_at` заполнены;

## Важное про разрешения

Минимизировать запросы владельцу.

- Read-only Git-проверки, локальные тесты и обычные проверки выполняй автономно, если среда позволяет.
- Не делай повторный `fetch`/`merge` только ради формальности, если текущая задача уже локально доступна и HEAD подходит.
- Для повторяющихся безопасных read-only команд допустимо использовать ранее разрешённые similar commands.
- Реальный запуск `bot.py` с Telegram API — отдельное внешнее действие: перед первым запуском запроси одно явное подтверждение владельца.
- После запуска не проси новые разрешения на каждую локальную read-only проверку.
